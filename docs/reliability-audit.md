## Work order and exit gates

1. **R1–R2 REST architecture:** stop repeated 1015/cooldown loops and prove selected Entry cannot be starved.
2. **R3–R5 live feed and scanner:** prove reconnect, symbol-cap, rolling coverage, and scanner request budget.
3. **R6–R9 Entry pipeline:** official option identity, 9-strategy candle evidence, one risk-plan calculation and exact 2R+ result.
4. **R10–R14 UI/runtime/status:** prevent client-side request amplification and misleading readiness.
5. **R15 release proof:** CI + Verify, manual deploy approval, market-open FYERS verification, rollback/restore evidence.

## Release definition — do not mark complete until all pass

- No unexplained 429/1015 burst; caller attribution identifies every upstream request.
- One REST scheduler controls every broker REST request; scanner/warmup cannot outrank Entry.
- After 429 or process restart, background traffic remains blocked; only a single controlled recovery probe can be sent at a time. If provider cooldown cannot be proven clear, remain blocked rather than retry.
- WebSocket reconnect restores exactly the desired subscription set without duplicate subscriptions and stays under FYERS account cap.
- F&O coverage is explicitly rolling; no stale symbol is presented as live Top Gainer.
- Selected underlying + official option contract + fresh ticks + contiguous completed candles all verify.
- All nine strategy tests pass positive and negative cases; Entry/SL/Target and RR >= 2 are independently asserted.
- Health endpoint distinguishes service alive from trading ready; UI cannot show READY on stale data.
- No overlapping UI polling; live APIs are never cached by service worker.
- Production deploy remains manual, orders disabled for verification, and deployed SHA is verified.
